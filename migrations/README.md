# Database initialization

Run one script for each configured instance, regardless of its region.
These scripts initialize new installations. Use an administrator for setup and
a separate account for the running service.

| Database | Script |
| --- | --- |
| Supabase Database | `supabase/001_create_keepalive_tables.sql` |
| Oracle Cloud ADB | `oracle/001_create_keepalive_log.sql` |
| Oracle Cloud MySQL | `mysql/001_create_keepalive_logs.sql` |

Each database stores `id`, `ping_time`, `status` and `request_id` in one log table.
Record IDs are generated by the database. Timestamps use UTC, and a unique
request-ID index makes retries safe.

All four columns are required. The shared schema is an auto-generated numeric
primary key, a microsecond-precision UTC timestamp without a timezone component,
`status` of up to 16 characters, and `request_id` of up to 36 characters. Each
table has a unique request-ID index and a `(ping_time DESC, id DESC)` history index.
SQL type names differ by engine: PostgreSQL/Oracle use `TIMESTAMP(6)` and MySQL
uses `DATETIME(6)`. UTC defaults are explicit and independent of session timezone.

## Upgrading the legacy tables

The `002_normalize_utc_schema.sql` files upgrade the pre-migration tables once;
do not apply them to a new table already created by `001`. Back up data and schema
first, verify timestamps/statuses are non-null and statuses fit 16 characters.
For Oracle and MySQL, verify existing timezone-less values are already UTC.
PostgreSQL converts its legacy `timestamptz` values explicitly to UTC.
Missing legacy request IDs receive unique IDs; existing IDs and timestamps are
preserved. Oracle and MySQL DDL is not transactionally reversible like PostgreSQL.

- **Supabase:** run the script in the SQL editor. Row-level security is enabled;
  public roles have no table access. The service uses a server-side secret key.
- **ADB:** run the script as the schema user exposed through ORDS. If another
  account owns the table, grant SELECT and INSERT and create a synonym.
- **MySQL:** replace the script's `keepalive` database name with the configured
  Hyperdrive database name. Create a TLS-required service account with SELECT and INSERT
  permissions, restricted to the actual connection source.

Configure credentials as described in [deployment](../README.md#deploy-with-github-actions), then
start the service and check that every enabled instance loads on the dashboard.


## Optional retention

No database changes are needed while `retention` is `false` (the default).
Before enabling cleanup:

- **Supabase:** apply `supabase/003_retention.sql` once, for new and existing
  installations. This installs a service-role-only RPC and grants DELETE on the
  log table. The RPC runs with the caller's privileges and validates the same
  minimums (3 days or 12 rows). Applying the script does not delete any history.
- **Oracle:** the owning ORDS schema can already delete its records. If using a
  separate runtime account, grant DELETE on the log table in addition to SELECT
  and INSERT.
- **MySQL:** grant DELETE on `keepalive.keepalive_logs` to the existing runtime
  account, keeping its host restriction and TLS requirement. No new table or
  routine is needed. MySQL 8+ is required for row-based retention.

Only the check-in log table is cleaned. Retention does not alter the schema or
reset ID sequences. Disable it in configuration to stop future deletion;
previously deleted records require a backup to restore.
